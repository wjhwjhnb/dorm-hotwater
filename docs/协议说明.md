# 协议说明

> 本文记录这套东西是怎么被研究出来的：接口、签名、以及**踩过的每一个坑**。
> 目的有两个：让想改代码的人少走弯路，以及说明这个工具到底在做什么。
>
> 研究对象：微信小程序 `wxc83b34a65e93b730`（乐校通系水电控）。
> 方法：**纯静态**分析解包产物（`app-service.js` 等），无注入、不改客户端。

## 一、⚠️ 最重要的一条：这个系统里有**两套互不相干的请求层**

**这是整件事最大的坑。** 一开始按 A 家族的签名去敲 B 家族的路径，服务端一直回
`-67 系统异常`；换域名、调单双斜杠、带整条 cookie、预热会话……全都无效。

|  | 家族 A | 家族 B |
|---|---|---|
| 封装 | `util/util.js` 的 `fnJson` | `V4/v4-util.js` 的 `fnJson` |
| 域名路由 | `util/url.js` | `V4/v4-url.js` |
| 签名 | `X-Sign = md5("1FF75E512" + F)` | `sign = md5(token + timestamp + "A70893")` |
| 额外头 | `X-Ghost`、`x-token` | `timestamp`、`token` |
| 域名 | `topservice.lxt6.cn` / `v3-app.lxt6.cn` | `ai.lxt6.cn/api`、`sos-api.lxt6.cn/api` |
| 覆盖 | 登录、`user/**`、`mgapp/**`、`bath/valve/*` | `/cus/**` 等新平台接口 |

**结论：本项目用家族 A。**

家族 B 的 `/cus/**` 接口在 `v3-app` 上**永远返回 `-67 系统异常`**，
而且它有独立的账号体系（同一个手机号去 `ai.lxt6.cn/api` 登录会返回"账号/密码错误"）。
所以 `openDevice_4G`、`getOpenResult_4G`、`customerPersonLogin` 这类接口对本账号不可用，
**不用再试了**（我试过三个域名，全是 -67）。

### 怎么确认真实域名（别靠猜）

小程序 webview 的 Chromium 磁盘缓存里残留着**明文请求 URL**：

```
%APPDATA%\Tencent\xwechat\radium\web\profiles\webview_<账号哈希>\Cache\Cache_Data\data_*
```

```bash
grep -aohE 'https://[A-Za-z0-9._-]*lxt6\.cn(?::[0-9]+)?/[A-Za-z0-9._/?=&%-]{2,160}' data_* | sort -u
```

注意：小程序自己的 `usr/miniprogramLog/log1` 只有 WMPF 层 API 调用、**没有**应用请求 URL，
别去那儿浪费时间。另外 `POST` 请求不进缓存。

## 二、签名（家族 A）

### X-Sign

```js
X-Sign = md5(v3_md5 + F)

POST -> F = JSON.stringify(body)          // 就是实际发出去的那串，键顺序也要一致
GET  -> F = "k=v&k=v"                     // 按对象字面量顺序，不含 "?"

v3_md5 = "1FF75E512"                       // 硬编码在 util/secret.js
v3_sid = "2021011300001"                   // X-Sid 头
```

md5 实现末尾是 `.toLowerCase()` → **签名是小写**。

> ★ **GET 的参数也要参与签名** —— 这条最容易漏。
> ★ **坑：`requests` 会把 Python 的 `True` 序列化成 `"True"`，而签名里用的是 `"true"`。**
> 两边不一致 → 服务端回 `-301 数据安全校验不通过`。
> 必须显式转成 JS 语义字符串再传：
> ```python
> params = {k: ("true" if v is True else "false" if v is False else str(v))
>           for k, v in data.items()}
> ```
> 这个坑我一头撞进去过，报错信息完全看不出原因。

### X-Ghost —— 设备时间指纹

```js
J(t)  = t.toString(16).padStart(12,'0').toUpperCase()   // 毫秒时间戳的 hex
E(h)  = 逐字节求和 % 256  -> 2 位大写 hex
R(h)  = 逐字节异或        -> 2 位大写 hex
X-Ghost = E(h) + h + R(h)                                // 共 16 位
```

例：`8701A12EC445AEA1`
```
时间戳 01A12EC445AE = 1791785977262 ms
累加 (01+A1+2E+C4+45+AE)%256 = 0x87  ✓
异或 01^A1^2E^C4^45^AE      = 0xA1  ✓
```

**★ 它不是随机数。** 填随机值服务端会回 `-45 请求已过期,请核对设备时间!`
—— 错误信息其实已经提示了是"时间"问题。

### 请求头

```
content-type : application/json
X-Sid        : 2021011300001
X-Sign       : md5("1FF75E512" + F)
X-B3-TraceId : 16 位随机小写十六进制
X-B3-SpanId  : 同上
X-Product-Ver: 3.11.3#?release
X-Mobile-Info: windows#?PC#?Windows 10 x64
X-Ghost      : 见上
x-token      : <纯值>              ← 服务端把 x-token 当纯值回显
Cookie       : tokenInfo=<纯值>    ← Cookie 里要带 "tokenInfo=" 前缀
```

## 三、登录：**手机号 + 密码 + 图片验证码，没有短信**

### 流程

```
① GET  https://topservice.lxt6.cn/user/authentication/getCode
        ?account=<手机号>&topservice=true
   -> {"Code":0,"Data":"data:image/jpeg;base64,..."}      图片验证码

② POST https://topservice.lxt6.cn/user/login/userLoginV2
        {"studentMobile":"..","loginPassword":"..",
         "code":"<图片验证码>","topservice":true}
   -> {"Code":0,"Data":{"studentId":"..","url":"https://v3-app.lxt6.cn","state":0}}
      响应头 Set-Cookie: tokenInfo=<studentId>#?<32位hex>
```

- **密码是明文**（前端唯一用到 RSA 的地方是支付宝服务商接口）
- **token 不在返回体里**，在 `Set-Cookie` 的 `tokenInfo`
- 会话寿命较长：实测**隔了 10 小时以上仍然有效**
- 失效时所有接口返回 `-44 用户身份失效`，`src/valve.py` 会自动重新登录并重试原请求

### ★★ 最大的误解：`code` 字段是图片码，不是短信码

参数名叫 `code`，很容易以为是短信验证码。**不是。**

我一开始搞错了，去调了 `moblieMessageV2` 发短信——**那是"忘记密码"流程**
（对应 `user/modify/loginPasswordByAuthenticationMessage`），跟登录毫无关系。

**实测证据**（用假密码 + 真图片码）：

```
POST userLoginV2 {"studentMobile":"10000000000",
                  "loginPassword":"WrongPassword_TEST_123",
                  "code":"05270","topservice":true}
-> {"Code":-45,"Message":"登录账号或密码不正确!,还有2次机会!"}
```

服务器说的是**密码**不对 —— 说明验证码 `05270` **已经被接受了**。
如果 code 是短信码，这里应该报"验证码错误/已过期"。

**所以：登录全程不需要短信。**

### ⚠️ 服务器限制尝试次数

上面那句 `还有2次机会!` 是警告：**密码错误几次会锁号**。
所以密码必须一次输对，不要反复试。验证码识别错了会自动换一张重试，**那不消耗密码机会**。

### 验证码识别

用 [ppllocr](https://pypi.org/project/ppllocr/)（纯 ONNX，内置模型，CPU 推理 <150ms）。
这个 5 位数字验证码实测识别率 **5/5**。识别错了也没关系——验证码可以无限重取，
代码里就是重试循环（`src/lxt_login.py` 的 `auto_login`，默认最多 8 轮）。

**不上打码平台**：要钱、要联网、要把用户验证码图片发给第三方，而本地模型足够了。

**不用 captcha_trainer 那类框架**：要标注几千张样本 + 长时间训练 + 数 GB 体积，
Python 3.12+ 还跑不起来。没必要。

## 四、设备

### 按 MAC 查设备

```
GET /mgapp/machine/getMachineByMac?mac=<带冒号的MAC>&typeId=1
-> {machineId, machineName, siteId, siteFlag, mtype, cnflag, roominfo, deviceVer}
```

> ★ **MAC 必须带冒号**（`48:87:2D:00:00:01`）。传纯 `AABBCCDDEEFF` 返回空。
> 小程序里 `getDeviceAddressType` 正是先插冒号再请求。

```
GET /mgapp/machine/getCache?machineId=<machineId>&typeId=1
-> {base:{...}, ali4G:{aliGroup, imei, isFlag, productType}}
```

### 按宿舍号找设备（一键配置用的就是这条）

```
① baseDict/site/getLowerAreas?areaId=<schoolId>
   -> 区域 / 楼栋 / 楼层 三级树（叶子是楼层）

② baseDict/site/getDormitoryOrPublicRoom?areaId=<楼层id>&typeId=1
   -> [{"id":"660000000000000001","name":"402",
        "demo":"某校区15栋4层402","siteFlag":0}]
       ★ 这里的 id 就是后面要用的 siteId

③ bath/machine/status/getList?schoolId&investorId&siteId&siteFlag&typeId
   -> {"idleNum":1,"usedNum":0,
       "machineStatusList":[{"machineId":"...","machineName":"402",
                             "addressMsg":"某校区15栋4层402",
                             "curStatus":0,"curStatusMsg":"空闲"}]}
```

`schoolId` / `investorId` 从这两个接口拿：

```
user/binding/getSchoolInfo              -> schoolList
operation/getInvestorInfoByShoolidV2    -> investorInfo.investorId
```

### 为什么要"选"而不是自动定

**房号会重名。** 实测某校 1343 个房间里 `"402"` 有 4 个（13/14/15/16 栋各一个），
全库有 139 个重名房号。更麻烦的是还有 `A402 / B402 / C402` 这种**真实存在**的房号 ——
它们只是名字里含 "402"，并不是 402。

> **原则：精确匹配和"含有"都必须列出来，靠排序和分组区分。**
> 绝不能把"含有"的过滤掉 —— 否则住 A402 的人就永远找不到自己的宿舍。
> 打分规则见 `src/discover.py` 的 `_score()`。

### 死路（记下来别再试）

- `mgapp/machine/getInfoByQRCode`：传整条二维码 URL / `?` 后串 / 印刷号，一律 `Data=null`
- `mgapp/machine/getMachineByLocation`：**只支持 POST**（GET 报 `Request method 'GET' not supported`），
  且同样需要先知道 `siteId`，对"按名字找"没帮助

## 五、开阀 / 关阀 / 状态（**服务器下发，不需要蓝牙**）

```
开阀  POST /bath/valve/open
      {typeId, channelWay, machineId, deviceVer,
       machineInfoJson:{lastPosMoney:"0000", lastPosSerial:"0000"}}
      -> {offline:1, offlineDuration:7, communicationVal:"5B15"}
         ★ communicationVal 关阀/查状态必须回传

关阀  POST /bath/valve/close
      {typeId, channelWay, machineId, deviceVer,
       machineInfoJson:{machineId, communicationVal}}
      -> {communicationVal:"9A5A"}

状态  GET  /bath/valve/getStatus?typeId&machineId&modeValue&communicationVal
```

实测开阀 **0.29 秒**、关阀 **0.24 秒**。

**接口设计上的一个特点**：`communicationVal` 只在"开阀"的返回里下发。
所以如果本地没有开阀记录，`getStatus` 就查不了 —— 那说明阀门处于关闭/空闲状态。
这不是故障，是接口就这样。

### 零成本预检

不想真出水验证参数格式？用**不存在的设备号**调 `open`：

```python
{"machineId": "0000000000000000", ...}
-> Code=-45  设备[0000000000000000][1]未授权，请联系管理员0!
```

服务端**认出了设备号并做了校验** ⇒ 参数形态正确 ⇒ 换成真设备号就能开。
`python cli.py probe` 就是干这个的。

### 怎么判断是 4G 机还是蓝牙机

查 `util/version.js` 里的能力表，按 `deviceVer` 第二段（`machinever`）+ `typeid`：

以 `deviceVer="01,07"`、`typeid=1` 为例：

| 函数 | 表 | 结果 |
|---|---|---|
| `NBCanUse` | `["02","03","04","05"]` | ❌ |
| **`FourthGCanUse`** | 长表，含 `"07"` | **✅** |
| `pureBleCanUse` | `["00,00","00,01","00,06"]` | ❌ |
| `smpBleCanUse` | `["00,02",...]` | ❌ |

→ 这是 **4G 机**（`getCache` 里的 `ali4G` + IMEI 也印证了），
**开阀和关阀都走服务器下发，不需要蓝牙。**

> 只有**蓝牙机**关阀才需要 BLE：`V4/v4-nbBle.js` 的 `closeBleMac` 会连设备发 `cmd=14`。

## 六、旧路径：蓝牙直连（备用）

如果你的设备是蓝牙机，走的是这条。已经实现并验证过，代码在
`src/lxt_ble.py` / `src/lxt_nb.py` / `src/lxt_open.py`。

### 帧格式（发送）

```
A5  <len>  <d>  <g>  <c1>  <c2>  <c3>  <data...>  <sum>

d, g   各 1 字节随机数
c1 = u(rns1, g, d)
c2 = u(rns0, g, d)
c3 = u(cmd,  g, d)
len    = 5 + len(data)            ← 即 <len> + 3 == 帧总字节数
sum    = 全部字节累加 & 0xFF
u(x, t, r) = (0xAA + (x ^ t ^ r)) & 0xFF

整体转义：A5 → 1BE7，1BE7 → 1B00E7（A5 是帧头，载荷里出现会歧义）
```

### 帧格式（接收）

```
A5 <len> <rns3> <rns2> <rns1> <rns0> <cmd> <type> <ver> <way> <status> <data...> <sum>
i(x, t, r) = ((x - 0xAA) & 0xFF) ^ t ^ r     解码时 t = rns2, r = rns3
```

### 命令表

| cmd | 作用 | data |
|---|---|---|
| `F0` | 取设备信息 | 空 |
| `08` | 取随机数 | 空 |
| `02` | 授权（服务器令牌） | `type(1B) + ID(8B)`，type=`01` |
| `01` | appKey 授权（**本地可算**） | 见下 |
| `06` | 开阀 | `type(1B) + systemData(16B) + systemTime(6B)` |
| `14` | 关阀 | `"00" + ID(8B)` |

### cmd 01 的密钥是纯本地计算的

```js
get01AppKey(randomHex, 当前秒数):
    每个字节  r = (255 - (byte + seconds)) & 0xFF

getXorData(data, key):
    每 8 字符一段做变换

send01({appKey, randonNum, xorData, time})
```

**没有任何硬编码密钥** —— 只要拿到设备的随机数（cmd 08）和当前时间就能构造。
源码里走这条路的分支是"非 5xx 流程"。

### 蓝牙路径的坑

- **帧长规则**：`<len>` + 3 == 帧总字节数。对不上说明 BLE 通知分包了，必须拼包再判断。
  我一开始收到的 `a5 1c` 一直不被接受，就是因为它被拆成了 19+12 两段。
- 设备被占用时 `cmd 02` 会回一个很短的状态码（`03` 设备正忙 / `06` 该账户正在使用中），
  **不是**完整的 26 字节挑战数据 —— 别把它当成"帧格式错了"。
- `cmd 06` 回 `01` = **授权失败**（令牌被拒），不是"设备忙"。

## 七、常见错误码

| Code | 含义 |
|---|---|
| `0` | 成功 |
| `-44` | 用户身份失效，需重新登录（`valve.py` 会自动重登重试） |
| `-45` | **多义**：X-Ghost 算错 / 图片验证码错 / 密码错 / 设备未授权 |
| `-67` | 系统异常（多半是敲了家族 B 的接口） |
| `-301` | 数据安全校验不通过（签名不对，常见于 GET 的 `True` vs `"true"`） |
| `-302` | platform 值错误 |

## 八、.bat 的坑（血的教训，改了三次）

Windows 批处理有两个非常隐蔽的陷阱，**我前后各踩了一次，表现完全不同但根因同类**：

### ① `.bat` 的**内容**必须纯 ASCII

cmd 用**系统 OEM 码页**（中文系统是 GBK）解析 `.bat`。内容里任何非 ASCII 字节
都会被拆成乱码指令，整个脚本崩掉。

```
call "%~dp0一键配置.bat"     ← 中文在内容里 → 变成乱码指令 → '开热水.bat was unexpected at this time.'
```

**中文只能出现在【文件名】里**：`一键配置.bat` 的内容是
`call "%~dp0SETUP.bat"`，真实逻辑放在 ASCII 文件名的 `SETUP.bat` 里。

### ② `if ( ... )` 块里不能有裸括号

cmd 用 `)` 判断块的结束，`echo` 行里一个未转义的 `)` 会把整个块**静默截断**：

```bat
if not defined PYEXE (
  echo   (current user only, no admin rights needed)    ← 块在这里被截断
  call :install_python
)
```

后果：`PYEXE` 的检测结果全部失效，**明明装了 Python 却跑去下载安装**。
要用 `^(` `^)` 转义。

### ③ 自检方法

写完 `.bat` 一定要跑：

```bash
# 内容不能有非 ASCII 字节
python -c "d=open('x.bat','rb').read(); print(sum(1 for b in d if b>127))"   # 必须是 0
```

`make_release.py` 和 `setup.py` 的 `make_launchers()` 里都已经内置了这个检查。

## 九、Python 环境相关的坑

- **微软商店版的 `python.exe` 是个假壳子**（在 `%LOCALAPPDATA%\Microsoft\WindowsApps`），
  装不了依赖。所有脚本都会显式跳过这个路径。
- 检测顺序：`py -3.x` → `py -3` → `where python`（排除 WindowsApps）→ 常见安装目录。
- 控制台需要 `sys.stdout.reconfigure(encoding="utf-8")`，否则中文输出会 `UnicodeEncodeError`。
- `requests` 要设 `trust_env=False`（不走系统代理），否则本机抓到包的代理会干扰。

## 十、调试建议

1. **先看是不是敲错了家族** —— `-67` 基本就是这个。
2. **`-301` 优先查 GET 参数的类型转换**（`True` vs `"true"`）。
3. **`-45` 别急着怀疑票据** —— 先看 X-Ghost 时间戳。
4. **`-44` 是唯一明确表示"要重新登录"的码**，这个可以放心自动重登。
5. **验证码识别失败不消耗密码机会**，可以放心重试。
6. **密码错误会消耗次数**，别拿真账号试探。
