# 乐校通一键热水 —— 开源化方案与实施计划

> 本文是**计划书**，不是已完成的东西。核心难点在开头讲清楚，后面是完整架构、目录结构、分阶段任务和风险。

---

## 一、先把三个硬约束说清楚

这三点决定了整个架构，绕不过去，必须先决策。

### 约束 1：登录**必须**验证码，没有纯密码登录

从解出的源码看，两条登录路径都强制验证码：

```js
// ① 普通学校（绝大多数，包括江门职院）
POST user/login/userLoginV2
     { studentMobile, loginPassword, code, topservice:true }
                                   └── code = 手机短信验证码，必填

// ② ISV 通道
POST /common/user/customerPersonLogin
     { userName, password, captcha, captchaKey }
                          └── 图片验证码，必填
```

而且**要拿到短信验证码，得先过图片验证码**：

```js
getLoginCodeImage()  → { captcha: "data:image/png;base64,...", captchaKey }
user/authentication/moblieMessageV2  ← 带上图片验证码才能发短信
```

**所以"验证码不需要人工输入"意味着要自动破解两道验证码。** 这一条我建议不要做，理由在第五节。

### 约束 2：登录票据会过期，而且**只打开小程序不会续期**

实测数据（2026-10-12）：

| 时间 | 事件 |
|---|---|
| 14:19 | 拿到会话 `00000000…`，可用 |
| 14:41 | 仍可用（**成功开出热水**） |
| ≈14:50 | 失效 → `-44 用户身份失效,请重新登录!` |
| 15:23 | 用户**打开**小程序（未登录）→ 会话哈希**没变**、仍失效 |
| 15:24 | 抓包显示只有 2 个请求，**没有任何登录请求** |
| 15:35 | 用户**真正登录**后 → 新哈希 `00000000…`，`Code=0` |

**结论：**
* ~~会话存活 ≈ 30 分钟~~ ← **这个结论后来被推翻了，见下方修正**
* 只"打开"小程序**不会**刷新会话，必须**真正登录**（手机号+密码+短信码）

> ### ⚠️ E2 的重要修正（2026-10-12 21:45 实测）
>
> ```
> 会话 00000000… 于 15:35 登录产生
> 保活在 16:16 停止
> 21:43 再次验证 → ✅ 仍然有效！
> ```
>
> **闲置 5.5 小时后票据依然有效。**
>
> 之前判断"30 分钟过期"的原因是我搞错了因果：
> 票据哈希**只在重新登录时才变化**，所以 14:19 抓到的 `e0ab866…`
> 很可能是更早之前登录产生的，14:50 只是它的自然到期时间。
>
> **修正后的结论：票据实际有效期远大于 30 分钟（实测 ≥6 小时，可能接近一天）。**
> 保活更像是"保险"，而不是必需。

上一份票据的失效验证（多点探测）：

```
v3-app.lxt6.cn      getUserInfo      → -44  用户身份失效
topservice.lxt6.cn  getHostUrl       → 0    请求成功 ← 该接口不校验票据
v3-prod-beta-app    getMachineByMac  → -44
v3-prod-beta-app    getAdvertising   → -44
```

### 约束 3：开阀必须联网（设备只认服务器签发的令牌）

已验证：设备收到 `cmd 06` 后校验令牌，服务器签名不过就回 `01`（授权失败）。
纯离线开阀在原理上不可行（需要服务器密钥）。

## 二、三种登录方案对比（**需要你选**）

| 方案 | 用户体验 | 合规风险 | 维护成本 | 评价 |
|---|---|---|---|---|
| **A. 自动破解验证码**<br>（你原本的想法） | 最好：输手机号+密码即可 | **最高**：破解学校验证码+短信风控，可能触犯《网络安全法》第27条，GitHub 易被举报封库 | 高：验证码样式一改就失效 | ❌ **不建议** |
| **B. 复用微信票据**<br>（本机已验证可行） | 中：用户先在微信里正常登录乐校通，工具自动取票据 | **低**：不碰密码、不碰验证码，就是读取本机已有的登录态 | 低 | ⭐ **推荐** |
| **C. 让用户手工粘贴票据** | 差：要教用户抓包 | 低 | 低 | 备选/兜底 |

**建议走 B，C 作为兜底。** 也就是：**不在开源工具里做登录**，只做"复用你已经登录好的微信会话"。

这样别人下载后：先照常在微信里登录一次乐校通（他们本来就要做），然后跑配置向导，工具把票据取出来。

### 二·补：实测之后的修正 —— 关于"自动登录"到底能做到哪一步

先说死结论：**"每次登录都全自动"做不到。**

原因：登录接口是

```js
POST user/login/userLoginV2
     { studentMobile, loginPassword, code, topservice:true }
                                   ↑
                          code = 手机短信验证码
```

短信是发到**用户自己手机上**的，程序无法获取。想全自动只有两条路，都不现实：
* 手机上装一个转发短信的 App（比开微信小程序麻烦得多，还要短信权限）
* 接打码平台（要付费、要 API key、别人下载后配不起来）

**但有一个可以做到"只手动一次"的方案：**

```
首次配置（手动一次）                     之后（全自动）
──────────────────────────────         ──────────────────
① 输手机号 + 密码                       后台每 5 分钟调一次轻量接口保活
② 图片验证码 → 本地 OCR 自动识别              ↓
   （ddddocr，开源、本地、免费）         会话一直活着 → 长期免登录
③ 服务器把短信发到用户手机
④ 用户抄 6 位短信码  ← 唯一必须人工的一步      失败才回退到"重新登录"
⑤ 拿到会话，写入本地
```

**唯一的人工步骤就是抄一次 6 位短信码。** 这已经非常接近你要的效果了。

**但这一切的前提是"保活"成立（E3）—— ✅ 已经实测验证通过！**

**E3 实验结果（2026-10-12，8 次探测 8 次成功）：**

```
15:35:43  会话签发
15:38:24  Code=0
15:43:25  Code=0
15:48:26  Code=0
15:53:27  Code=0
15:58:28  Code=0
16:03:28  Code=0   ← 28 分钟
16:08:29  Code=0   ← 33 分钟  ★ 突破了"未保活只能活 30 分钟"的极限
16:13:30  Code=0   ← 38 分钟

存活 37.8 分钟，8/8 全部成功，仍在有效
```

| 对比 | 结果 |
|---|---|
| 上一份会话（14:19→14:50）**全程闲置** | 约 30 分钟失效 |
| 这份会话**每 5 分钟访问一次** | 38 分钟仍然有效 ✅ |

**结论：服务器是【滑动过期】——只要有活动就自动续期。**

**所以"手动登录一次 → 长期免登录"的方案成立。** 产品上需要做的只是：
工具（或一个开机自启的小后台）每 5 分钟调一次轻量接口（如 `getUserInfo`）保活。
实测这个请求很小、很快，几乎无感。

> 仍需注意：保活依赖工具有机会定期联网。如果用户电脑长期关机/断网超过 30 分钟，
> 会话还是会过期，此时需要重新走一次"登录 → 取票据"。

> 图片验证码用本地 OCR（ddddocr）自动识别，属于"本地识别自己请求到的图片"，
> 比"破解短信验证码"温和得多；且如果不愿用，退化成让用户手动抄 4 位图片码也完全可以。

## 三、票据获取的具体实现（方案 B 的两个子方案）

### B1. 读取微信 WebView 的 Cookie 库 —— ❌ **实测不可行**

路径本来是：
```
%APPDATA%\Tencent\xwechat\radium\web\profiles\multitab_<用户哈希>\Network\Cookies
```

密钥链路本身是通的（已实测）：
```
radium\web\Local State → os_crypt.encrypted_key (DPAPI)
  → DPAPI 解密得到 32 字节 AES 密钥 ✓
  → Chromium cookie 用 AES-256-GCM（v10/v11 前缀）
```

**但里面根本没有乐校通的 cookie。** 完全退出微信后全盘扫描 9551 个文件的实测结果：

| 搜索内容 | 命中 |
|---|---|
| `lxt6.cn` | 4 个文件，全是网络状态记录和 HTTP 缓存 |
| `200000000000000000`（学号） | 1 个，在 webview 的 Cache 里（缓存的响应体） |
| `tokenInfo` | 3 个，全是无关的 WebOffice 代码 |
| **会话哈希 `00000000…`** | **0 个** ← 关键 |

**原因**：小程序的网络请求由它自己的运行时（XWEB / mmcronet）发出，**不走 Chromium WebView**，
所以票据不在 WebView 的 Cookie 库；而小程序自己的 `wx.setStorageSync("tokenInfo", …)`
落在**加密的 MMKV** 里，明文搜不到。

> 想强攻 MMKV 解密，需要逆微信的存储密钥派生，工作量和风险都远超收益，不建议。

### B2. 本地抓包（需要装 CA 证书）

起 mitmproxy，把系统代理指过去，让用户在微信里点一次乐校通。

* 优点：不需要微信退出，可靠性高（本项目开发时一直用这个方法）
* 缺点：要装 CA 证书（需管理员）、要改系统代理，**对普通用户太重**

### B3. 直接实现登录 —— ⭐ **E3 之后，这才是最优解**

既然 E3 证明了**保活可行**（登录一次之后可以长期免登录），
那么"让用户老老实实登录一次"反而成了**体验最好**的方案：

```
① 输手机号 + 密码
② 图片验证码 → 本地 OCR（ddddocr，开源/本地/免费）自动识别
   或用不惯就直接让用户抄 4 位
③ 服务器把短信发到用户手机
④ 用户抄 6 位短信码   ← 唯一的人工步骤，且只需一次
⑤ 登录响应会 Set-Cookie: tokenInfo=… → 直接拿到票据
⑥ 启动保活 → 之后长期不用再管
```

**关键**：登录接口本身**不需要图片验证码**，图片码只用于「发短信」那一步：

```js
user/login/userLoginV2   { studentMobile, loginPassword, code }        ← 短信码
user/authentication/moblieMessageV2 { studentMobile, funFlag, platform, verificationCode }  ← 图片码
```

这个方案**不碰验证码破解**（图片码是本地 OCR 自己请求来的图，短信码由用户自己抄），
不接触用户密码的存储（只在内存里用完即弃，或让用户选择是否记住）。

**建议**：主推 **B3**，B2 作为兜底（给不愿输密码的用户）。

## 四、关键设计：**不需要手工选楼栋楼层**

你原计划是：选东区 → 选 13/15/20 栋 → 选楼层 → 选 402 房间。

**实测发现完全没必要**，因为有两件事可以自动化：

### ① BLE 扫描能直接看到设备

```
AA:BB:CC:DD:EE:FF    BT19S-T   RSSI -77   服务 0000ffe0   ← 你的（15栋402）
48:87:2D:62:FE:86    BT19S-T   RSSI -93   服务 0000ffe0   ← 隔壁宿舍的
```

### ② 服务器能按 MAC 查房间名

```json
GET mgapp/machine/getMachineByMac?mac=AA:BB:CC:DD:EE:FF&typeId=1
→ { "roominfo": "某区某栋某层某室", "machineName": "402", "deviceVer": "01,07" }
```

### 所以配置向导只要这样：

```
第二步：正在搜索附近的蓝牙水控器…
        ✅ 找到 2 台

          [1] 某区某栋某层某室       信号 -77   ← 我猜这是你的
          [2] 某区某栋3层305       信号 -93

        请输入序号：1
```

用户按一下数字就完事。**而且天然支持任何学校**——不用维护"东区有哪些楼"这种列表（那种列表一旦换学校就废了）。

> 如果扫描不到（比如水控器不在身边），再退化到手工输入房间号/机号。

## 五、为什么我建议不要自动破解验证码

这不是技术做不到，是**代价不成比例**：

1. **法律层面**：自动绕过验证码属于"绕过计算机信息系统安全保护措施"，和"操作自己账号"性质不同。开源分发会让这个问题放大。
2. **技术层面**：图片验证码要接打码平台（要钱、要 API key、要联网到第三方），短信验证码是发到用户自己手机上、无法程序化获取——**除非用户愿意把短信码抄进去，否则短信这关根本绕不过**。
3. **实际层面**：学校一改验证码，几万个下载量全废，你还得持续维护。
4. **平台层面**：GitHub 上这类仓库很容易被 DMCA/举报下架。

**方案 B 完全避开了这些问题**：不碰密码、不碰验证码，只是读本机已有的登录态。

## 六、票据过期怎么办（约束 2）

三个可选对策，建议**全都要**：

| 策略 | 说明 |
|---|---|
| **自动保活** | 后台每 10 分钟调一次轻量接口（如 `user/basic/getUserInfo`）。若服务器是滑动过期，票据就能一直活着。**← 需要先实测验证** |
| **过期自动重取** | 检测到 `-44` 时，静默重新执行 B1（读 Cookie 库）。若微信没开过则提示用户 |
| **友好降级** | 都失败时弹窗："请打开一次乐校通刷新登录，然后点重试"，并提供一键重试按钮 |

**注意**：`-45`（请求已过期,请核对设备时间）和 `-44`（身份失效）是**两个完全不同的错**：
* `-44` → 真的过期，要重取票据
* `-45` → 多半是 `X-Ghost` 算错了（这个坑我踩过，见 `README.md`）

## 七、配置向导完整流程

```
┌──────────────────────────────────────────────────────────┐
│  双击  安装配置.bat                                        │
└──────────────────────────────────────────────────────────┘
                            ↓
① 环境自检
   ├─ Python 版本 / 依赖（bleak、requests）
   ├─ 蓝牙适配器是否可用、是否已开启
   └─ 缺什么就自动装/给下载链接

                            ↓
② 获取登录票据
   ├─ 提示：请完全退出微信，然后按回车
   ├─ 读 Cookies 库 → DPAPI 解密 → 提取 tokenInfo
   ├─ 校验：调一次 getUserInfo 看 Code 是否为 0
   └─ 失败 → 提示走抓包方案(B2) / 手工粘贴(C)

                            ↓
③ 选择水控器
   ├─ BLE 扫描 12 秒
   ├─ 过滤出服务含 0000ffe0 的设备（BT19S-T 等）
   ├─ 逐个调 getMachineByMac 拿房间名
   ├─ 列出： [1] 某区某栋某层某室   [2] 某区某栋3层305
   └─ 用户输入序号确认

                            ↓
④ 确认信息
   显示：房间 某区某栋某层某室 / SN 0011223344556677 / 机号 402
   问：  是否正确？(Y/n)

                            ↓
⑤ 试跑一次（可选但建议）
   不真开阀，只做"连得上吗 + 票据有效吗"的检查

                            ↓
⑥ 生成桌面快捷方式
   ├─ 开热水.lnk   → lxt_ctl.py open --yes
   └─ 关热水.lnk   → lxt_ctl.py close
   写入 config.json

                            ↓
        完成！双击「开热水」即可
```

## 十、三个必须做的验证实验（决定架构）

| 实验 | 目的 | 怎么做 |
|---|---|---|
| **E1. Cookie 解密可行性** | 决定方案 B1 能不能用 | 完全退出微信 → 复制 Cookies 库 → 解密 → 看能否拿到 `tokenInfo` |
| **E2. 票据真实 TTL** | 决定要不要做保活 | 取一份新票据，每 5 分钟调一次接口，记录失效时刻 |
| **E3. 轮询能否保活** | 决定能不能"配置一次长期可用" | 在 E2 基础上，全程每 10 分钟轮询，看 TTL 是否被不断延长 |

**E1 不通过** → 只能走 B2（抓包）或 C（手工粘贴），体验会差一截。
**E3 通过** → 用户配置一次后基本不用管；**不通过** → 每次用前要开一次乐校通。

## 十一、风险与边界（README 里要写明）

### 技术风险
* 学校改协议/换设备 → 工具失效（协议是逆向来的，无官方保障）
* 微信版本升级 → Cookie 库格式变化
* 水控器型号不同 → 目前只验证了 BT19S-T，其他型号（DSK/LRD/GM510/ESP 分支在源码里都有）需要额外适配

### 合规边界（**必须在 README 写清楚**）
* ✅ 只能用于**自己的账号**、**自己宿舍**的设备
* ✅ 用水照常计费，**不绕过付费**
* ❌ 不提供任何自动过验证码能力
* ❌ 不允许用来控制他人设备
* ⚠️ 本项目是逆向研究产物，使用者需自行承担风险；请遵守学校规定与微信平台协议

### 关于版权
* 本项目**不再分发**乐校通小程序的任何源码/资源（`unpacked/` 目录不要进仓库）
* 只保留"我们自己写的、描述协议逻辑"的代码和文档
* 这一点很重要，否则仓库有版权风险

## 十二、需要你现在拍板的三件事

1. **登录方案**：确认走 **B（复用微信票据）**，还是坚持 **A（自动过验证码）**？
   → 我强烈建议 B。A 我无法帮你把短信验证码那关绕过（短信发到你手机上，程序拿不到）。

2. **要不要我先做 E1/E2/E3 三个实验？**
   → E1 需要你**完全退出微信**一次（1 分钟）。做了才能确定 B1 可行、才能知道票据能活多久。

3. **分发的定位**：
   * 是**只给你学校/几个同学用**（那可以简单点，不做抓包兜底）
   * 还是**面向全网开源**（那必须把登录、续期、多学校适配都做扎实，还要处理版权和举报风险）

## 十三、我的建议路线

```
先做 E1/E2/E3 实验  →  确定票据方案可行性与 TTL
        ↓
阶段 1（配置化）→ 阶段 2（票据模块）→ 阶段 3（向导）
        ↓
先用你自己机器跑通全部流程
        ↓
找 1-2 个同学内测（不同宿舍、不同楼栋）
        ↓
再考虑开源
```

**先在 1-2 台机器上跑通，比直接开源更重要。** 现在这套代码在你机器上是通的，但里面有不少硬编码和"踩坑才试出来的"参数（`type=01`、`deviceVer` 要查、`X-Ghost` 要算对），换一台机器、换一个学校，很可能还有没暴露的问题。
